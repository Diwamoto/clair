契約は次のとおり固定した。

- すべての編集範囲は`baseRevision`時点のUTF-16座標で指定する。複数編集は昇順に検証し、重複を拒否してから後方順に一括適用する。
- revision不一致、負値・範囲外、Unicode scalar途中のUTF-16範囲、重複編集は本文を変更せず拒否する。
- 適用成功時だけrevisionを1つ進め、変更通知には適用後文書の`changedRanges`、編集元、Undo単位を含める。
- selection変更は本文変更通知から分離し、revisionとsnapshot取得回数を増やさない。
- snapshotは`initialLoad`、`save`、`diff`を明示的に指定した呼び出しだけで取得する。

既存の`ProjectEditorTab`への引き継ぎは、タブがディスクパス・dirty状態・保存を引き続き所有し、初回ロード/保存/diff生成の境界で`model.snapshot(reason:)`を呼び、編集経路から`model.apply(transaction)`を呼ぶ形にする。今回のIssueでは保存処理の全面置換や本番ホストへの接続は行っていない。

### API利用例

```swift
let transaction = ProjectEditorTransaction(
  baseRevision: document.revision,
  edits: [ProjectEditorReplacement(
    range: ProjectEditorUTF16Range(location: 10, length: 4),
    text: "new"
  )],
  source: .agent,
  undoUnit: .suggestion
)
let change = try document.apply(transaction)
```

## 目的と前提

文書の差分更新・revision契約を実装する。これはネイティブエディタPoCの残作業であり、本番への無条件採用は決定していない。
開始前に[共通ルールと基準](README.md)、[PoC報告](evidence/poc-report.md)を読む。NE-00完了後のソースを基準にし、依存Issueの成果コミットと完了条件を確認してから着手する。

## 実施手順

1. 既存ProjectEditorTabの保存・dirty・外部変更・履歴・selection利用箇所を列挙する。
2. UTF-16範囲、置換文字列、基準revision、編集元、Undo単位を持つtransactionを定義する。複数編集の座標が編集前基準か逐次基準かを一つに固定する。
3. 範囲不正、古いrevision、Unicodeの不正境界を拒否し、transactionを原子的に適用する。選択通知は本文更新と分離する。
4. 初回ロード/保存/明示的diff生成に使うsnapshot APIと、変更範囲通知を実装する。公開Stringを毎入力で更新する設計を導入しない。

## 完了条件・検証

1. 挿入・削除・複数範囲・emoji・結合文字・古いrevision・不正範囲のテストが通る。
2. 選択変更でrevisionも本文snapshot取得回数も増えない。
3. 既存保存機能へ繋ぐ対応表とAPI利用例があり、後続が契約を推測せず使える。
