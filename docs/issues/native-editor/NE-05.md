## 実装記録（2026-09-09）

- `NativeEditorLifecycleState` で表示 cache と Tree-sitter解析 lifecycle を分離した。clean tabの表示解放時はrevisionを無効化し、late callbackを拒否するが、固定依存にidle/join APIがないため `parser_idle = null`、`fully_released = false` を保持する。
- `Document` は表示 controllerと `RevisionAwareHighlightProvider` を同時に解放する経路へ変更した。dirty本文、Undo/Redo、marked text、pending proposalは従来どおり解放しない。再表示時はcontroller・providerを再生成し、本文・selection・scrollを復元する。
- `NativeEditorPolicy` のUTF-8 bytesとUTF-16長を独立に検証し、native上限超過文書はPoCのfallback viewへ送る。fallbackではnative controller/Tree-sitterを生成せず、境界値と理由を表示する。
- 状態は `open` のままとする。10MBを含む非同期解析でclose後のparser停止完了を証明するには、固定したCodeEditSourceEditorへjob cancel handleとidle/join契約を追加する必要があり、今回のPoC側だけでは完了条件1/2を満たせない。

## 再調査記録（2026-09-08）

共有側の基準 `HEAD` は `0e4ddae5e25063c6afae47ab03e426ff9caed8c9`、SwiftPMで固定した `CodeEditSourceEditor` は `1fa4d3c3ffba007482111466cb9721416f97ae00` である。固定revisionの実装を読み直し、既存APIだけで10MB close後の解析jobを安全に止め、停止完了を待つ方法があるかを確認した。

- `TreeSitterClient.setUp` は内部の `executor.cancelAll(below: .all)` を呼ぶが、その直後に新しい `.reset` jobを投入する。close専用のcancel handleではない。
- `TreeSitterClient.applyEdit` は新しいedit開始時に低優先度jobをcancelし、`queryHighlightsFor` は結果callback以外のcancel handleを返さない。どちらもclose後に呼べるAPIではない。
- `TreeSitterExecutor` と `cancelAll` は `package`/internal scopeで、consumerであるPoCから呼べない。upstream自身もcancelについて「即時停止を保証しない」としている。parse側は `Task.isCancelled` を周期的に確認するだけである。
- `TreeSitterExecutor` にqueueが空になるまで待つ、実行中jobをjoinする、idleを通知する公開APIはない。callbackはcancel後もmain queueへ到着し得る。
- PoCの `RevisionAwareHighlightProvider` はedit/query callbackのgenerationを検査してstale結果の適用を防ぐが、jobの実行停止・in-flight数の把握・close時のgeneration invalidationを提供しない。`Document.highlightProvider` は `Document` が保持し続けるため、`releaseDisplayCache()` でcontrollerだけをnilにしてもclient/executorの寿命は終わらない。

以上から、generation gateだけを追加して「解放済み」と扱うのは不正確であり、`setUp` の副作用をclose cancelとして利用するのも新しいparseを発生させるため安全な解決ではない。NE-05の完了条件1/2を満たすには、upstreamに job単位のcancel、generation付きcompletion、cancel完了後のidle/joinを公開する変更（または同等のfork）が必要である。今回はPoCの依存やupstreamを改変せず、状態を `open` のままとする。

## 目的と前提

メモリ保持を調べてタブ解放・大規模ファイル方針を作る。これはネイティブエディタPoCの残作業であり、本番への無条件採用は決定していない。
開始前に[共通ルールと基準](README.md)、[PoC報告](evidence/poc-report.md)を読む。NE-00完了後のソースを基準にし、依存Issueの成果コミットと完了条件を確認してから着手する。

## 実施手順

1. PoC累積RSS約1.1GiBを再現し、単独ファイルの新規プロセス測定と複数ファイル保持測定を分ける。
2. 通常/1MB/10MB/長行/50タブでprocess footprintとRSSを採り、close後のcontroller・parser・delegate・viewの解放を検証する。
3. 不要な参照や解析ジョブを解放する。非表示文書の表示キャッシュ解放と、dirty本文/Undoを守る方針を実装する。
4. ファイルbyte数、UTF-16長、最大行長に基づくnative対象範囲とfallback条件を記録する。大きいファイルで既存Webが安全と仮定しない。

## 完了条件・検証

1. 各fixture単独/累積/close後の測定値と計測時刻がある。
2. closeした文書の解放をテストし、再オープンやタブ復帰で本文・選択・Undoが仕様通り保たれる。
3. fallback/制限表示の条件を数値で記述し、その境界のテストがある。

## 対象外

dirtyタブやUndoの無断破棄、ユーザー文書での破壊的負荷試験。
